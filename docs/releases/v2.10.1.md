# v2.10.1

## 改进 / Improvements

### 中文

- **Server 事件循环阻塞治理（阶段 1）**：新增 `epub_browser/server_concurrency.py`，集中提供三个相互隔离的线程池与统一 offload 入口：
  - `run_db`（4 线程）：所有 `StateStore` / SQLite 同步调用；
  - `run_render`（2 线程）：EPUB/PDF 页面渲染、CSP 计算、AI 阅读正文准备等 CPU 密集工作；
  - `run_io`（2 线程）：书籍上传落盘、词典查询/安装/媒体读取等长耗时 IO。

  原先在 `async def` 处理函数里直接执行的同步调用会占住唯一的事件循环线程，使无关请求（含 `/api/health`）排队等待慢渲染；现在这些工作统一移出事件循环，零散短小的单次读取仍走 anyio 默认线程池。
- **每请求开销内存化**：`SetupStateMonitor` 缓存管理员存在性判定（`/setup` 成功后立即生效；管理员删除/角色变更触发重新校验；后台每 5s 兜底；尚未初始化时最多每 100ms 探测一次）；`StatKeyedCache` 以 `(mtime_ns, size)` 缓存 `asset-manifest.json`，文件未变化时零解析开销，资源重新发布后下一次请求自动重建。
- **覆盖范围**：`server.py`（认证、账户、管理后台、书库、页面与安全头）、`public_api.py`（PAT/OpenAPI 路由改为 `async` 并 offload）、`ai_reading.py`（AI 阅读提交、管理员重试、任务与结果读写）、`webhooks.py`（投递认领、收尾与历史清理）。
- 新增 `tests/test_server_concurrency.py`（7 个用例）与方案文档 `docs/plans/2026-11-07-server-event-loop-blocking.md`。

### English

- **Server event-loop blocking remediation (phase 1)**: Added `epub_browser/server_concurrency.py` with three isolated thread pools and a single offloading policy:
  - `run_db` (4 threads): all synchronous `StateStore` / SQLite calls;
  - `run_render` (2 threads): CPU-bound work such as EPUB/PDF page rendering, CSP computation and AI reading material preparation;
  - `run_io` (2 threads): long file IO such as book upload writes, dictionary lookup/installation and media reads.

  Previously, synchronous calls executed directly inside `async def` handlers held the single event-loop thread, making unrelated requests (including `/api/health`) queue behind a slow page render. Those calls are now offloaded; short one-off reads still use AnyIO's default limiter.
- **Per-request overhead moved to memory**: `SetupStateMonitor` caches the administrator-existence check (effective immediately after `/setup` succeeds; revalidated on admin deletion or role changes; 5s background fallback; at most one probe per 100ms while uninitialised). `StatKeyedCache` caches `asset-manifest.json` by `(mtime_ns, size)`, so unchanged files cost no parsing and asset republication automatically rebuilds the cache on the next request.
- **Coverage**: `server.py` (auth, account, admin, library, pages and security headers), `public_api.py` (PAT/OpenAPI routes converted to `async` and offloaded), `ai_reading.py` (AI reading submission, admin retry, job/result reads and writes) and `webhooks.py` (delivery claim, finalisation and history cleanup).
- Added `tests/test_server_concurrency.py` (7 tests) and the plan document `docs/plans/2026-11-07-server-event-loop-blocking.md`.

## 修复 / Fixes

### 中文

- 修复 Server 模式下 SQLite、文件读写与模板渲染直接运行在事件循环上导致的并发请求阻塞与排队问题。线程池为模块级单例并在进程退出时通过 `atexit` 关闭，测试中重复调用 `create_app()` 不再泄漏线程。
- 修复资产清单与 setup 状态改为内存缓存后可能出现的一致性问题：清单解析失败仍抛出原异常（不沿用旧清单、不改变公开资源判定）；管理员被移除后重新探测状态，避免把已登录用户误判回安装流程。

### English

- Fixed concurrent requests blocking and queuing in Server mode because SQLite calls, file IO and template rendering ran directly on the event loop. Pools are module-level singletons shut down via `atexit`, so repeated `create_app()` calls in tests no longer leak threads.
- Fixed consistency risks introduced by caching the asset manifest and setup state: a failed manifest load still raises the original exception (no stale manifest, no change to public-asset decisions), and setup state is re-probed after administrator removal so signed-in users are not pushed back into the setup flow.

## 说明 / Notes

### 中文

- **无对外行为变化**：URL、Cookie 属性、缓存头、304/ETag/Range/416、SSE 事件名、`{"code","message"}` 错误体、CSP 计算规则、i18n 文案与 SSG 输出均保持不变。本阶段不做 FastAPI 迁移，不引入 `APIRouter` / `Depends` / Pydantic。
- **不升级内容缓存修订**：`SERVER_OUTPUT_REVISION`、`PDF_OUTPUT_REVISION`、`PDF_METADATA_SCHEMA_VERSION` 均未改动，`content/` 与 `pdf/` 缓存结构不变；按既有约定只需重启/部署，不需重新转换书籍。
- 客户端断开不会中断已提交到线程池的工作（与 `run_in_threadpool` 的取消语义一致）。每个输出目录仍由 `runtime.py` 的目录锁保证单个 Server 进程，缓存 TTL 仅为多 worker/多实例部署的兜底。

### English

- **No externally observable behaviour changes**: URLs, cookie attributes, cache headers, 304/ETag/Range/416, SSE event names, `{"code","message"}` error bodies, CSP computation, i18n copy and SSG output are unchanged. This phase does not migrate to FastAPI and introduces no `APIRouter` / `Depends` / Pydantic.
- **No content-cache revision bump**: `SERVER_OUTPUT_REVISION`, `PDF_OUTPUT_REVISION` and `PDF_METADATA_SCHEMA_VERSION` are untouched, and the `content/` and `pdf/` cache schemas are unchanged. Per the existing convention, a restart/deploy suffices — no book reconversion.
- A client disconnect does not cancel work already submitted to a thread pool (same cancellation semantics as `run_in_threadpool`). `runtime.py`'s directory lock still enforces one Server process per output directory; cache TTLs are only a fallback for multi-worker/multi-instance deployments.

## 升级说明 / Upgrade notes

### 中文

- Server 模式：拉取新版本后**重启服务**即可；无需重新转换 EPUB/PDF，无需数据库迁移，无新增配置项。
- SSG 模式：本版本无静态输出变化，按惯例重新构建站点即可。
- 运维提示：新增 3 个线程池（合计最多 8 个工作线程），高并发部署可留意线程数与 SQLite 连接数；单目录单进程约束不变。

### English

- Server mode: after pulling the new version, **restart the server**. No EPUB/PDF reconversion, no database migration and no new configuration are required.
- SSG mode: there are no static-output changes; rebuild the site as usual.
- Operations note: three new thread pools add up to 8 worker threads. On high-concurrency deployments, watch thread and SQLite connection counts; the one-process-per-directory constraint is unchanged.
