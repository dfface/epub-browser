# EPUB Browser 阅读器功能调研与差异化建议

> 调研日期：2026-08-26。范围：Kindle、微信读书、京东读书、起点读书、掌阅 iReader。竞品事实优先采用厂商官网、帮助中心和由开发者发布的 App Store 页面；表中“有”仅代表在该来源中得到明确证实，并不表示功能完整度相同。

## 结论先行

EPUB Browser 不应试图复制内容平台的书城、付费、广告或大规模公域社区；这些能力依赖版权库存、供给和运营，和“私有 EPUB 书库”的产品边界不相称。

真正值得补齐的是两层能力：先达到现代阅读器的**听读、可访问性、检索/查词、连续数据体验**底线；再把已有的“可追溯 AI 阅读”延伸为**读书后仍可复用的私有知识系统**。后者是最有机会形成特色的方向：主流产品有问书、导读或 X-Ray，但没有把读者自己的 EPUB、精确证据锚点、个人标注、跨书联系和可携带导出，作为一个私有且可验证的闭环来做。

## 当前项目基线（避免重复建设）

当前仓库已具备：EPUB 私有书库的 SSG/Server 双模式、离线静态阅读、书架、进度、文本/图片标注、跨书标注中心、标注文本分享/下载，以及 Server 下按账户隔离的进度、标注、书架、访问控制和带原文证据的 AI 导读/问答。详见 [中文 README](readme/README.zh-CN.md)、[标注中心设计](superpowers/specs/2026-08-18-annotation-center-design.md) 和 [AI 原生阅读说明](ai-native-reading.md)。

本次以当前代码和已交付文档为准；`personal-reading-insights` 是待实现设计，不能当作现有能力。下列“缺口”也只指当前仓库中未发现同等的用户界面与持久化能力，而不是对未来计划的否定。

## 高置信度优先级

### P0：现代阅读底座——听读、检索、查词与可访问性

做一个不依赖内容平台的“朗读跟随”模式：章节级播放/暂停、速度与声音选择、当前句高亮、离开页面/切换章节时安全停止；将当前位置同普通阅读进度统一。首版可以优先调用浏览器或操作系统 TTS，清楚提示各浏览器语音质量与离线可用性差异，避免把读者的 EPUB 默认发送给外部语音服务。

同时补上 EPUB 全文索引、目录/结果跳转、词典与翻译提供者的显式选择，以及键盘导航、减少动态效果、阅读标尺、低视力主题和可访问名称。它们服务所有书籍、所有读者，也为 AI 与学习功能提供稳定的文本定位基础。

**模式与数据边界：**本地 TTS、搜索索引和阅读外观应能服务 SSG；Server 只同步用户偏好/进度。EPUB 文字索引若写入 `content/`，它才是内容缓存 schema 的一部分；UI、语音偏好、可访问性开关和 Server API 不应提高 Server 内容修订。

### P1：把“原文证据 AI”做成私有知识闭环

建议命名为“阅读卡片/知识脉络”，而非又一个泛化聊天框：

- 从用户划线、AI 证据或手动选词，一键生成带**书名、章节、原文片段、稳定锚点和来源链接**的卡片；用户可编辑、合并、标记“待核实”。
- 为人物、概念、论点建立可视化关系；每条关系回到至少一处原文证据。与 Kindle X-Ray 的单书静态说明相比，支持读者的私有补充与跨书联系。
- 支持按标签、实体、问题、时间和书籍检索；可把“我标过但没理解的内容”排成复习队列。间隔复习和自测题应是可选的学习模式，不能把小说阅读变成打卡负担。
- 导出为 Markdown、JSON 和 CSV（包含引文、锚点、笔记、标签与生成时间）；以后可增加 Obsidian/Notion 通用目录导出。现有纯文本标注分享继续保留。

这是最适合项目的差异化：模型输出必须可追溯到私有原文，用户编辑后的知识属于用户而非平台推荐流。知识卡、个人向量/索引、复习状态、导出任务均为 Server SQLite 数据；SSG 只保留本地可用的基础标注/导出，绝不嵌入账户或 AI 凭据。

### P1：先落地“个人阅读洞察”，再增加可选目标

仓库已有未实施的私有评分/书评与真实阅读时长设计，方向正确：先完成个人日/周/月阅读时长、按书/章节回顾和隐私隔离，再加入每日分钟/页数目标、连续阅读日、计划与温和提醒。微信读书的数据回顾和阅读挑战证明此类需求存在，但本项目应以“自我回顾”而非公开排行榜为核心。

所有会话、目标和提醒都应是 Server 运行时数据；SSG 不出现相关 API 或误导性入口，也不需重新转换 EPUB。

### P2：小而可信的共读，而非公域社区

在已有账户、书籍授权和 AI spoiler-free/read-so-far 语义上，提供“阅读小组”：管理员或书主邀请成员；在一本书/一章/一个原文锚点留下讨论；支持仅自己、组内、完成本章后可见三种范围；默认不推送、不公开索引。可选的每周问题由现有 AI 章节问题生成，但发送前由组主审核。

这样吸收微信读书/起点的共同阅读价值，又避免冷启动、审核、垃圾内容和隐私风险。该项应在个人数据与内容权限模型稳定后再做。

### P2：面向私有书源的“连载与书库管家”

对被 `--watch` 监测的书源，识别新增章节或 EPUB 更新，显示“本书已更新/上次阅读位置之后有 N 章”，并提供不剧透的变更摘要。书库层面可以按已读主题、作者、标签、未完成进度和个人评分给出“下一本读什么”，候选只来自用户已授权的书。

它把起点的更新提醒和推荐逻辑转化为私人书库价值，不需要售卖内容，也不把用户阅读历史交给广告推荐系统。

## 不建议当前投入

1. **书城、版权购买、会员、打赏或广告**：与自带 EPUB 的商业模式和信任承诺冲突，且需要完全不同的内容/支付/风控能力。
2. **开放式书评、热门划线、动态广场**：需要内容审核、反垃圾、排序与隐私治理；对私有部署的净收益低。
3. **先做大量文件格式转换**：PDF/MOBI/AZW3 的渲染与版权/版式兼容成本高。先把 EPUB 阅读、证据定位和导出体验做成优势；只在明确用户需求后再评估导入管线。
4. **浏览器端自由手写优先于基础可访问性**：手写很吸引人，但受设备、笔和定位精度限制；TTS、键盘、检索与低视力支持覆盖更广。

## 推荐路线图与验收信号

| 阶段 | 交付 | 成功信号 |
| --- | --- | --- |
| 1（底座） | 书内搜索、查词/翻译、朗读跟随、无障碍设置 | 读者可不离开章节完成搜索、理解和听读；TTS 不造成进度错乱。 |
| 2（留存） | 已规划的私人阅读洞察 + 目标/提醒 | 数据只对本人可见；跨时区、离线补传和多标签页不会重复计时。 |
| 3（特色） | 证据型阅读卡、跨书知识脉络、结构化导出 | 每张 AI/用户卡片都能回到原文；导出可被外部笔记工具直接使用。 |
| 4（可选社交） | 权限受控的共读与防剧透讨论 | 未授权用户不能枚举书、讨论或 AI 结果；默认私密且无需公域运营。 |

每一阶段都应分别验证 SSG 与 Server：共享阅读器能力保持静态可用；账户、协作、洞察和 AI 只在鉴权后的 Server 中出现。仅当 EPUB 派生内容缓存的 schema/语义变化时，才提高 `SERVER_OUTPUT_REVISION`；页面、i18n、偏好、SQLite 用户数据和前端资源更新不应触发全书重转。

## 来源与可信度说明

- Kindle：Amazon 官方产品页、KDP 帮助和 Kindle 帮助中心（高）。
- 微信读书：腾讯官方 GitHub 仓库与 App Store 上腾讯开发者自述（高；App Store 版本记录会随版本变动）。
- 京东读书、起点读书：App Store 上相应开发者的产品页/版本记录（高；功能可随版本调整）。
- 掌阅：iReader 官方官网（高）。

本文件只将上述来源直接支持的功能视为竞品事实；产品策略与优先级是基于项目边界做出的推断，而非来源的原文主张。
